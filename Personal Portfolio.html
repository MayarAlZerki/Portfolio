Conversational risk-analytics assistant Built the text-to-q half Brokers ask questions in plain language; the system answers with validated KDB+/q queries against live trading data. Show detailsHide details

The flagship. A multi-specialist agent routes each question to a product-manuals expert or a database expert, each with its own private message channel so tool noise never pollutes the conversation.

  • A dedicated validation stage checks function-call shape, date-window limits, and identifier formats across a whole multi-statement q script before anything executes.
  • Execution errors come back as structured payloads with repair hints the model can act on, capped by an automatic retry policy.
  • Schema and curated few-shots are served as deterministic tools rather than embeddings, because schema lookup must never be probabilistic.

Stack: LangGraph, KDB+/q, PostgreSQL checkpointing, streaming FastAPI, LangSmith.

Public website assistant Primary author A customer-facing assistant whose retrieval strategy changes with the shape of the question. Show detailsHide details

Designed and built end to end. The distinctive piece is temporal retrieval: a classifier routes each question to one of four strategies — from hybrid search with exponential time-decay reranking down to a plain database sort when "latest news" needs no embeddings at all.

  • A lightweight local ONNX classifier acts as a zero-cost, deterministic prompt-injection firewall in front of the LLM.
  • Lead-capture tools take zero model-generated arguments — contact details come only from validated user profile state, which eliminates hallucinated emails and phone numbers by design.
  • Redis-backed answer caching and per-conversation rate limiting keep cost and abuse in check.

Stack: LangGraph, pgvector with hybrid search and HNSW, ONNX Runtime, Redis, FastAPI.

Multi-tenant trading assistants Core contributor One codebase answering traders' questions over WhatsApp, a CRM web app, and a mobile platform. Show detailsHide details

The safety model here is my favorite pattern: the model only writes SQL against virtual tables, and a rewriting layer expands them into real queries with the tenant's identity hard-coded into every predicate. A user cannot reach another account's rows no matter what SQL the model emits.

  • Built the recommendation engine's full lineage — TF-IDF and logistic regression, then sentence embeddings, then graph-based retrieval where adjacent nodes become "you might also want to ask" suggestions.
  • Shipped an LLM email-template generator with an adversarially hardened prompt that treats system triggers, not free-text descriptions, as the source of truth.

Stack: LangGraph, PostgreSQL, Chroma graph retrieval, S-BERT, Twilio.

Text-to-SQL over order-flow data Early architect, ongoing contributor Analytical questions over an FX/CFD platform's order flow, answered with rewritten, guarded SQL. Show detailsHide details

I contributed from the earliest chain-based version — conversational question reformulation, few-shot retrieval, new report types built end to end — through its agentic rewrite.

  • Generated queries pass through a rewriting engine that inlines domain functions as CTEs with column pushdown, argument validation, and strict time-window caps.
  • Large results are diverted to downloadable files, so the model never sees bulk data — a token-cost control and a leakage control at once.

Stack: LangGraph, PostgreSQL, SQLAlchemy, FX/CFD domain modeling.

RAG-as-a-service platform Own deployment topology One config-driven retrieval service, exposed over MCP and REST, replacing duplicated RAG pipelines. Show detailsHide details

Each product declares its knowledge base, chunking, and retrieval contract in one config file; the service exposes exactly one authenticated retrieval tool per project.

  • Fully incremental sync — content fingerprinting plus chunk-level hashing means a nightly run over an entire knowledge base typically re-embeds nothing.
  • I own the containerization: healthchecked vector-database services, cron-driven syncs, and a slim production image.
  • Benchmarked open-source ONNX embedding models as a self-hosted alternative to API embeddings.

Stack: MCP, FastAPI, pgvector, Chroma, Docker Compose, ONNX Runtime.

How I build

  • Guardrails by constructionSafety properties hold even when the model misbehaves — enforced in the execution layer, not requested in the prompt.
  • Errors are dataFailures return as structured payloads a model can repair from, and users always get a graceful answer instead of a 500.
  • Retrieval fits the questionNot every question deserves an embedding search. The right strategy per query beats one pipeline for everything.
